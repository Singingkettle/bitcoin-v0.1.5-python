# 第 6 章　交易与 UTXO 模型

> **本章目标**：弄明白比特币里的"钱"到底是什么、一笔交易由哪些部分组成，
> 并且逐字节读懂史上第一笔比特币转账。
>
> **对应源码**：[bitcoin/tx.py](../bitcoin/tx.py)　　**实验**：[labs/lab05_transaction.py](../labs/lab05_transaction.py)

## 6.1　两种记账方式

假设要设计一个记账系统，最自然的想法是**账户模型**——银行就是这么做的：

```text
账户        余额
小明        50
小红         0          小明转 10 给小红  ──►   小明 40，小红 10
```

比特币**不是**这样记账的。它用的是一种更像**现金**的方式，叫 **UTXO 模型**
（Unspent Transaction Output，未花费的交易输出）。

想象你的钱包里没有"余额"这个数字，只有几张面额各异的钞票：一张 50 的，一张 20 的，一张 3 块 7 毛 2 的。
比特币世界里，这些"钞票"就是 UTXO，它们有几个特点：

* **面额任意**：可以是 50 BTC，也可以是 0.00000001 BTC；
* **每张都写着"归谁所有"**（一把只有主人能打开的锁）；
* **只能整张花掉，不能撕开**：你要付 10 块，手里只有一张 50 的，那就把这张 50 的交出去，同时收回一张 40 的找零；
* **花掉就作废**：旧钞票销毁，同时凭空印出新钞票，新钞票面额之和不能超过旧钞票。

**一笔交易，就是"销毁几张旧钞票、印出几张新钞票"的一次操作。**

```text
      输入（销毁的旧钞票）                         输出（印出的新钞票）
   ┌──────────────────────┐                   ┌──────────────────────┐
   │ 小明的那张 50         │ ────────────────► │ 10  归小红            │
   └──────────────────────┘                   │ 40  归小明（找零）    │
                                              └──────────────────────┘
```

你的"余额"，是钱包软件把账本上所有"锁着你的名字、还没被花掉"的钞票的面额加起来的结果。
账本本身并不知道什么叫余额。

> **为什么要这么设计？** 账户模型需要处理"同一个账户的两笔交易谁先谁后"的问题；
> UTXO 模型里每张"钞票"只能被花一次，是否双花一目了然——只要看这张钞票是不是已经被别的交易花过了。
> 不同钞票之间的交易互不相干，可以按任何顺序验证。

## 6.2　交易的结构

```text
交易 CTransaction
├── nVersion            版本号（4 字节，目前是 1）
├── vin[]               输入列表
│   └── CTxIn
│       ├── prevout         指向被花掉的那张"旧钞票"
│       │   ├── hash            它在哪笔交易里（那笔交易的哈希，32 字节）
│       │   └── n               是那笔交易的第几个输出（4 字节）
│       ├── scriptSig       "钥匙"：证明我有权花它（通常是一个签名）
│       └── nSequence       序列号（4 字节，通常是 0xFFFFFFFF）
├── vout[]              输出列表
│   └── CTxOut
│       ├── nValue          面额，单位是聪（8 字节）
│       └── scriptPubKey    "锁"：规定谁能花这张新钞票
└── nLockTime           锁定时间（4 字节，通常是 0）
```

（`v` 开头的变量是中本聪的命名习惯：`vin` = vector of inputs，输入的数组。）

注意**输入里没有金额**。输入只是一个指针："我要花掉某笔交易的第 n 个输出"。
那个输出的面额是多少，要顺着指针去找那笔交易才知道。也注意输入**不能只花一部分**——
指到哪个输出，就是整个花掉。

[tx.py](../bitcoin/tx.py) 里的类和上面这棵树一一对应。比如"指针"：

```python
class COutPoint:
    """"某笔交易的第 n 个输出"——用 (交易哈希, 序号) 精确指向一笔钱。"""

    def __init__(self, hash_: int = 0, n: int = UINT_MAX):
        self.hash = hash_      # 前一笔交易的哈希（uint256，用 int 表示）
        self.n = n             # 那笔交易的第几个输出；原版的 -1 在这里就是 0xFFFFFFFF
```

## 6.3　手续费藏在哪里

交易里**没有"手续费"这个字段**。规则是：

> **手续费 = 输入的总面额 − 输出的总面额**

输入比输出多出来的部分，归挖到包含这笔交易的那个区块的矿工。

这也意味着：如果你花一张 50 的"钞票"付了 10 块，**却忘了写找零的那个输出**，
那么剩下的 40 就全部成了手续费，送给了矿工。历史上真的有人因此损失惨重。钱包软件会替你处理找零，
但如果你将来自己手写交易，务必记住这一点。

## 6.4　钱最初从哪来：coinbase 交易

每笔交易的输入都指向更早的交易的输出，那最早的输出从哪来？

每个区块的第一笔交易是特殊的，叫 **coinbase 交易**（币基交易，和后来那家同名的公司无关）。
它只有一个输入，而且这个输入**不指向任何东西**（`hash` 全 0，`n` = 0xFFFFFFFF）：

```python
    def is_coinbase(self) -> bool:
        """coinbase 交易：只有一个输入且该输入指向"空"。每个区块的第一笔交易，凭空造出区块奖励。"""
        return len(self.vin) == 1 and self.vin[0].prevout.is_null()
```

它凭空"印"出新的比特币（一开始每个区块 50 BTC），付给挖出这个区块的矿工。
**这是比特币唯一的发行方式。** 世界上存在的每一个聪，顺着输入的指针一路往回追溯，
最终都会到达某个区块的 coinbase 交易。

coinbase 的输入既然不需要"钥匙"，它的 `scriptSig` 字段就空了出来，矿工可以往里面写任意内容（2~100 字节）。
中本聪在创世块的 coinbase 里写下了那句著名的报纸标题（第 8 章）。

## 6.5　解剖史上第一笔转账

2009 年 1 月 12 日，中本聪付给密码学家 Hal Finney 10 个比特币。这是人类历史上第一笔比特币转账，
记录在第 170 号区块里。它的全部内容只有 275 个字节：

```text
0100000001c997a5e56e104102fa209c6a852dd90660a20b2d9c352423edce25857fcd3704000000004847304402
204e45e16932b8af514961a1d3a1a25fdf3f4f7732e9d624c6c61548ab5fb8cd410220181522ec8eca07de4860a4

```

用第 2 章学的知识，我们可以拿着"手术刀"从头往后切：

| 字节 | 内容 | 含义 |
|---|---|---|
| `01000000` | nVersion | 版本 1（4 字节小端） |
| `01` | 输入个数 | 变长整数：1 个输入 |
| `c997a5e5…7fcd3704` | prevout.hash | 被花掉的钱所在的交易（32 字节，**字节序与显示相反**） |
| `00000000` | prevout.n | 那笔交易的第 0 个输出 |
| `48` | scriptSig 长度 | 0x48 = 72 字节 |
| `47 3044…0901` | scriptSig | `47`="压入 71 字节"；然后是 DER 签名 `3044…09` + 1 字节的 `01` |
| `ffffffff` | nSequence | 序列号 |
| `02` | 输出个数 | 2 个输出 |
| `00ca9a3b00000000` | vout[0].nValue | 0x3b9aca00 = 1,000,000,000 聪 = **10 BTC** |
| `43` | 脚本长度 | 0x43 = 67 字节 |
| `41 04ae1a…d84c ac` | vout[0].scriptPubKey | `41`="压入 65 字节"、公钥、`ac`=OP_CHECKSIG |
| `00286bee00000000` | vout[1].nValue | 0xee6b2800 = 4,000,000,000 聪 = **40 BTC** |
| `43 41 0411db…12a3 ac` | vout[1].scriptPubKey | 另一个公钥 + OP_CHECKSIG |
| `00000000` | nLockTime | 0 |

把被引用的交易哈希颠倒字节序，得到 `0437cd7f8525ceed…a597c9`——这是**第 9 号区块的 coinbase 交易**，
中本聪自己挖到的 50 BTC。

所以这笔交易说的是：

> "把第 9 号区块 coinbase 的那 50 BTC 花掉：10 BTC 给 Hal Finney 的公钥，40 BTC 给另一个公钥。"

那"另一个公钥"是谁的？是 `0411db93…`——和第 9 号区块 coinbase 的收款公钥**一模一样**。
也就是说，**40 BTC 的找零付回给了原来那把钥匙**。这正是 v0.1.5 的找零方式，
第 12 章你会在 `wallet.py` 里看到同样的逻辑。

输入 50，输出 10 + 40 = 50，手续费为 0。2009 年，所有交易都是免费的。

## 6.6　交易 ID

一笔交易的 ID，就是对它的全部序列化字节做两次 SHA-256：

```python
    def get_hash(self) -> int:
        """交易哈希（交易 ID）= 对整笔交易的序列化字节做两次 SHA-256。"""
        return int.from_bytes(hash256(self.serialized()), "little")
```

对上面那 275 个字节算一下，得到 `f4184fc596403b9d638783cf57adfe4c75c605f6356fbc91338530e9831e9e16`。
你可以去任何一个区块浏览器搜索这个 ID。

`tests/test_mainnet_vectors.py` 做了完整的验证：把这 275 字节反序列化成 `CTransaction` 对象，再序列化回去，
一个字节都不差；算出的 ID 与区块浏览器一致；而且——这是最关键的——
**用本项目的脚本引擎验证它的签名，通过**。关于签名是怎么验的，见下一章。

## 6.7　基本的合法性检查

一笔交易要被接受，得过很多关。第一关是 `check_transaction`——不需要任何上下文、只看交易本身就能做的检查：

```python
    def check_transaction(self) -> bool:
        """CheckTransaction：不依赖任何上下文就能做的基本检查。"""
        if not self.vin or not self.vout:
            return False                    # 输入和输出都不能为空
        for txout in self.vout:
            if txout.n_value < 0:
                return False                # 金额不能为负
        if self.is_coinbase():
            if not 2 <= len(self.vin[0].script_sig) <= 100:
                return False                # coinbase 的 scriptSig 必须是 2~100 字节
        else:
            for txin in self.vin:
                if txin.prevout.is_null():
                    return False            # 普通交易的输入不能指向"空"
        return True
```

后面几关需要查账本（第 10、11 章）：

* 输入指向的输出**存在吗**？
* 它**还没被花过吗**？（防双花）
* `scriptSig` 这把钥匙**打得开**那个输出的锁吗？（第 7 章）
* 输入总额 **≥** 输出总额吗？（不能凭空变钱）
* 如果花的是 coinbase，它**成熟了吗**？（要等 100 个区块）

> **历史上的一个教训**：你可能注意到上面只检查了"金额不能为负"，没有检查"金额不能太大"。
> v0.1.5 确实没有这个检查。2010 年 8 月，有人利用这一点构造了一笔交易：两个输出的金额都巨大无比，
> 加起来超出了 64 位整数的范围，"溢出"成了一个很小的数，于是通过了"输出总额 ≤ 输入总额"的检查，
> 凭空造出了 1844 亿个比特币。中本聪几小时内发布了修复补丁，整个网络回滚了那个区块。
> 这是比特币历史上最严重的一次事故（第 16 章）。
>
> Python 的整数不会溢出，所以这个具体的漏洞在本项目里不会以同样的方式出现，
> 但序列化时 `write_int64` 会因为数值过大而报错。

## 6.8　nSequence 与 nLockTime

这两个字段在 99.9% 的交易里都是默认值（`0xFFFFFFFF` 和 `0`），初学时可以先跳过。它们是中本聪为一种高级用法预留的：

* `nLockTime` 规定"在区块高度到达某个值之前，这笔交易不算定稿"；
* 没定稿的交易可以被**同样输入、但 `nSequence` 更高的新版本替换**。

设想两个人要频繁地互相付小额的钱：他们可以先签一笔"未来才生效"的交易，之后每次调整金额就签一个序列号更高的新版本，
全程不用上链，只有最终版本才被打包。这个构想后来因为安全问题被禁用了很多年，
但它的思想最终演化成了今天的**闪电网络**和**RBF**（手续费替换）。

对应的代码是 `tx.py` 里的 `is_final()` 和 `is_newer_than()`，以及 `mempool.py` 里的替换逻辑。
`tests/test_mempool.py` 末尾的三个测试演示了它。

## 本章小结

* 比特币没有账户和余额，只有一张张"钞票"（UTXO）；交易 = 销毁旧钞票、印出新钞票。
* 输入是指向旧输出的**指针** + 开锁的**钥匙**；输出是**面额** + 一把**锁**。
* 钞票只能整张花，所以需要**找零**；**手续费 = 输入总额 − 输出总额**，没有单独的字段。
* coinbase 交易凭空造币，是比特币唯一的发行方式；所有的钱都能追溯到某个 coinbase。
* 交易 ID = 整笔交易序列化后做两次 SHA-256。

## 思考题

1. 你有三个 UTXO：5、3、2 BTC。你要付给别人 6 BTC，手续费 0.01。请设计这笔交易的输入和输出。
2. 为什么交易的输入里不写金额？如果写了，会有什么麻烦？
3. 6.5 节那笔交易如果被人改掉了 `prevout.n`（从 0 改成 1），会在哪一关检查失败？

<details><summary>参考答案</summary>

1. 一种方案：输入 = 5 + 2（或 5 + 3）；输出 = 6 给对方，0.99（或 1.99）找零给自己。
   也可以三个全用上，找零 3.99。用哪几个由钱包的"选币算法"决定（第 12 章）。
2. 金额由被引用的那个输出决定，是"事实"而不是"声明"。如果输入里再写一遍，就多了一个需要检查"两边是否一致"的地方，
   平白增加了出错和作弊的机会。好的数据格式里，每个事实只应该出现一次。
3. 第 9 号区块的 coinbase 只有 1 个输出（序号 0），序号 1 不存在——在"输入指向的输出存在吗"这一关失败。
   即使存在，签名也会失效，因为 `prevout` 是被签名覆盖的内容之一。
