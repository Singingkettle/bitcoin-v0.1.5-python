# 第 12 章　钱包

> **本章目标**：弄明白钱包到底是什么（提示：里面没有钱）、"余额"怎么算、花钱时怎么挑"钞票"、

>
> **对应源码**：[bitcoin/wallet.py](../bitcoin/wallet.py)、`db.py` 的 `WalletDB`
> 　　**实验**：[labs/lab10_wallet.py](../labs/lab10_wallet.py)

## 12.1　钱包里没有钱

比特币"钱包"这个名字很有误导性。**币不在钱包里——币在区块链上**，
是交易索引里那些挂着"你的锁"、还没被花掉的输出（第 10 章）。

钱包里真正保存的是：

| 内容 | 对应原版 | 作用 |
|---|---|---|
| **私钥**（以及由它算出的公钥、公钥哈希） | `mapKeys`、`mapPubKeys` | 开锁的钥匙。**这是唯一真正重要的东西** |
| 和我有关的交易 | `mapWallet` | 为了算余额、显示交易记录，不必每次都扫描整条区块链 |
| 地址簿 | `mapAddressBook` | 给地址起的备注名，纯粹为了方便 |
| 设置 | `nTransactionFee` 等 | v0.1.5 里只有一项：自愿多付的手续费 |

所以"备份钱包"的本质是备份私钥；"钱包丢了"的本质是私钥丢了——币还在区块链上，只是再也没有人能花它了。
据估计，早期有数百万个比特币因为私钥丢失而永久沉睡。

## 12.2　哪些钱是"我的"

钱包判断一个交易输出是不是自己的，方法是看那把**锁**：

```python
    def is_mine_txout(self, txout: CTxOut) -> bool:
        """CTxOut::IsMine：这把"锁"是标准模板，而且对应的私钥在我手里。"""
        match = solver(txout.script_pubkey)         # 是两种标准锁之一吗？（第 7 章）
        if match is None:
            return False
        kind, data = match
        if kind == TX_PUBKEY:
            return bytes(data) in self.keys             # P2PK：锁里的公钥是我的吗
        return bytes(data) in self.keys_by_h160         # P2PKH：锁里的公钥哈希是我的吗
```

在此基础上定义两个量：

* **credit（收入）**：一笔交易的输出里，属于我的那些的金额之和；
* **debit（支出）**：一笔交易的输入里，花的是我的钱的那些的金额之和。

钱包通过两个"监听器"得知新交易：一个挂在**区块链**上（有交易进了区块），一个挂在**内存池**上（有新交易进池，即零确认）。
每来一笔交易，就问一句"和我有关吗"，有关就记进 `map_wallet`：

```python
        chain.tx_listeners.append(self._on_chain_tx)
        mempool.listeners.append(self._on_mempool_tx)
```

## 12.3　"余额"是怎么算出来的

钱包里**没有**一个叫"余额"的变量。余额每次都是现算的：

```python
    def get_balance(self) -> int:
        """GetBalance：所有"已定稿、未花掉"的钱包交易的可用金额之和。"""
        with self.chain.lock, self.lock:
            return sum(self.get_available_credit(w)
                       for w in self.map_wallet.values()
                       if self.is_final(w) and not w.f_spent)
```

三个条件：

1. **`not w.f_spent`**——这笔钱包交易里属于我的钱，还没被我花掉；
2. **`is_final`**——交易已经"定稿"（第 6 章的 `nLockTime`，绝大多数交易天然满足）；
3. **`get_available_credit`**——如果是挖矿所得，必须已经成熟，否则按 0 算：

```python
    def blocks_to_maturity(self, wtx: WalletTx) -> int:
        """GetBlocksToMaturity：挖矿所得还要再等几个块才能花。"""
        if not wtx.tx.is_coinbase():
            return 0
        return max(0, (params.COINBASE_MATURITY + 20) - self.get_depth(wtx))
```

**注意那个 `+ 20`。** 共识规则要求 coinbase 有 100 个确认才能花；但钱包自己更保守，要等 **120** 个。
原版界面上的说明文字也是这么写的（大意：生成的币要等 120 个区块才能花）。
多出来的 20 个块是安全余量：万一自己的节点和网络上其他节点对"现在到底有几个确认"的看法差了几个块，
也不至于发出一笔会被别人拒绝的交易。

### 零确认的钱也算

注意条件里**没有**"至少 1 个确认"。别人刚付给你、还在内存池里的钱，立刻就计入余额——2009 年的原版就是这样。
实验 10 第 5 步：

```text
   内存池里有 1 笔交易
   Alice 余额 287.66，Bob 余额 12.34
```

学过第 10、11 章之后你应该明白这是**不安全**的：零确认的交易可能永远不会上链（实验 12 里 Bob 的遭遇）。
原版的界面会把这种交易标成"0/unconfirmed"来提醒用户，6 个确认以下都带着"unconfirmed"字样。

## 12.4　整笔标记：v0.1.5 钱包最"原始"的地方

现代钱包按**每个输出**记录"花没花"。v0.1.5 的钱包粗糙得多：
每笔钱包交易只有**一个**标志 `fSpent`，管的是**整笔交易**。

```python
class WalletTx:
    """CWalletTx：一笔交易 + 钱包给它附加的信息。"""
    def __init__(self, tx, time_received, f_from_me=False, f_spent=False, hash_block=0):
        self.tx = tx
        self.time_received = time_received  # 钱包第一次见到它的时间
        self.f_from_me = f_from_me          # 是不是我自己发出的
        self.f_spent = f_spent              # 这笔交易里属于我的钱是否已被我花掉
        self.hash_block = hash_block        # 它被打包进了哪个区块（0 = 还没进块）
```

这带来一个直接的后果：花钱时，**必须把选中的那笔钱包交易里属于我的所有输出一次全花掉**，
不能只花其中一个——否则一个标志位没法表达"花了一半"。

## 12.5　花钱：create_transaction

假设 Alice 要付 12.34 BTC 给 Bob。钱包要做这些事（`create_transaction`，对应原版的 `CreateTransaction`）：

```text
1. 选币：从"可用的钱包交易"里挑出一些，面额之和 ≥ 12.34 + 手续费
2. 组装输出：
     vout[0] = 12.34 BTC，锁 = Bob 地址对应的 P2PKH
     vout[1] = 找零（如果选中的币比需要的多）
3. 组装输入：选中的每笔钱包交易里，每一个属于我的输出，各对应一个输入
4. 对每个输入签名
5. 算最低手续费；不够就加上，回到第 1 步重来
```

实验 10 第 4 步的真实输出：

```text
   这笔交易有 1 个输入、2 个输出：
      输出#0:  12.34 -> 1EgKCkmmYV3xHKY8Eu4zpe7SHy2N97WsiT  [Bob]
               锁：OP_DUP OP_HASH160 96090d71f54ea5ef29f67603e1b4f87b…
      输出#1:  37.66 -> 1P4VqxAwRrfJBN5YRCc3xzDrevHJovfZWb  [Alice（找零）]
               锁：0478019fb89d7b9ffeb80d7a2db7a22a102c12f5899f1d6223…
```

### 找零去了哪里

注意输出 #1 的锁：它不是 `OP_DUP OP_HASH160 …`（付给地址），而是 `<公钥> OP_CHECKSIG`（付给公钥）。
而且这个公钥，**就是被花掉的那枚币原来的公钥**：

```python
                if value_in > total_needed:
                    # vout[1]：找零。付回给第一枚币的同一个公钥
                    change_pubkey = None
                    for txout in coins[0].tx.vout:
                        if self.is_mine_txout(txout):
                            change_pubkey = self.extract_pubkey_mine(txout)
                            ...
                    tx.vout.append(CTxOut(value_in - total_needed,
                                          script_pubkey_for_pubkey(change_pubkey)))
```

原版源码在这里有一条注释，大意是：为了隐私，应该打乱输出的顺序，并且给找零用一把新的密钥——留作以后再做（todo）。

回头看第 6 章中本聪付给 Hal Finney 的那笔真实交易：输出 #1 的 40 BTC 找零，
付回的正是第 9 号区块 coinbase 的同一个公钥。**我们的钱包生成的交易，和 2009 年 1 月的那笔在结构上完全相同。**
`tests/test_wallet.py::test_change_goes_back_to_the_same_pubkey_like_the_original` 验证了这一点。

> 这个做法对隐私很不利：任何人一看就知道哪个输出是找零、哪个是付款。
> 后来的版本改成每次找零都用一把全新的密钥，并引入了"密钥池"（预先生成 100 把密钥备用，方便备份）。

### 选币算法

从一堆面额各异的"钞票"里，挑出哪几张来付款？这是个经典问题。`select_coins` 逐行移植自原版：

```text
1. 有恰好等于目标金额的，直接用它；
2. 把比目标小的放一堆，同时记住"比目标大的里面最小的那个"；
3. 小的全加起来都不够 → 只能用那个大的；
4. 否则用**随机试探法**（最多 1000 轮）找一个总和 ≥ 目标且尽量接近的子集：
     每一轮，第一遍对每个币掷硬币决定要不要；如果总和还不够，第二遍把没选的依次补上；
     记住见过的最好的方案；
5. 如果那个"大的"比找到的子集更接近目标，就用大的。
```

第 4 步解的是数学上著名的"**子集和问题**"——它没有高效的精确解法，所以用随机逼近。

这个算法有时会做出有点出人意料的选择。测试里记录了一个例子：钱包里有 9 份 5 BTC 的零钱和一枚 50 BTC 的整币，
要付 45 BTC。它宁可用 9 个小输入恰好凑出 45，也不去拆那枚 50 的整币
（`test_select_coins_prefers_exact_subset_of_small_coins_over_a_big_coin`）。
从"尽量不产生找零"的角度看，这是合理的。

## 12.6　提交与广播

交易签好之后（`send_money`，对应原版的 `SendMoney`）：

```python
            self.commit_transaction_spent(wtx)          # ① 记入钱包；把花掉的那些钱包交易标记为 f_spent
            if not self.mempool.accept(wtx.tx):         # ② 放进自己的内存池
                self._undo_commit(wtx)                  #    （失败则恢复钱包状态）
                return False, "交易无效，未能广播"
```

第 ② 步成功后，内存池的监听器会通知网络层向所有邻居通告这笔交易（第 13 章）。

原版在第 ② 步失败时是直接抛异常的（注释写着"这不应该失败"）。这里改成了把钱包状态恢复原样，算是一处小小的加固。

`send_money` 开头还有几项检查，对应原版"发送"对话框里的逻辑：金额必须大于 0、地址必须有效、
金额（加上手续费）不能超过余额。发送成功后，收款地址会自动加进地址簿。

## 12.7　三个容易被忽略的"善后"机制

**① 重启后把未确认的交易放回内存池**（`reaccept_wallet_transactions`）。内存池不落盘，重启就空了。
如果钱包里有发出去但还没进区块的交易，不放回去的话，就再也没人知道它、更没人打包它了。

**② 定期重播**（`relay_wallet_transactions`）。每当出现新的最佳区块时调用，但**最多每 10 分钟一次**：
把钱包里还没进区块的交易再向全网通告一遍。典型场景：你发交易的那一刻一个邻居都没连上。
`tests/test_integration.py::test_transaction_sent_while_offline_is_rebroadcast_later` 用真实的两个节点演示了这一点
——包括那个 10 分钟的节流。

**③ 被顶掉的挖矿所得**。你挖到的区块如果后来被更长的链重组掉了，钱包里那笔 coinbase 的确认数会变回 0，
`blocks_to_maturity` 变回 120，它自然不再计入余额。原版界面把这种交易显示为"(not accepted)"（未被接受）。

## 12.8　钱包的存储与安全

```python
class WalletDB:
    """wallet.sqlite——对应原版 CWalletDB。每条记录单独写入并立即提交，
    和原版"挖到块就马上把新私钥写盘"的行为一致：丢私钥 = 丢钱，不能攒着批量写。"""
```

四张表：`keys`（私钥）、`txs`（钱包交易）、`addressbook`（地址簿）、`kv`（设置）。

**私钥是明文保存的**——和 2009 年的 `wallet.dat` 一样。任何能读到这个文件的人（或者病毒）都能拿走你的全部比特币。
钱包加密功能要到 2011 年才出现。今天的最佳实践是把私钥放在根本不联网的设备里（硬件钱包、纸钱包）。

## 12.9　线程与锁（选读）

钱包会被好几个线程同时访问：界面线程在算余额，网络线程收到了新交易，矿工线程挖到了区块。
`wallet.py` 开头的注释立了一条规矩：

> 【加锁顺序】需要同时用到链和钱包时，一律先拿 `chain.lock` 再拿 `self.lock`。

为什么要规定顺序？设想线程 A 拿着钱包锁、等着要链锁；线程 B 拿着链锁、等着要钱包锁。
两个都在等对方先放手——永远等下去。这叫**死锁**。只要所有线程都按同一个顺序拿锁，就不可能出现这种循环等待。

（这份代码的早期版本恰恰在这里出过错：`get_balance` 先拿钱包锁再拿链锁，
而区块连接时是先拿链锁再回调钱包。界面刷新和挖矿同时进行时就可能卡死。
`tests/test_concurrency.py` 就是为了抓这类问题而写的：它同时开着矿工线程、两个"界面轮询"线程、
一个转账线程和一个喂区块的线程，检查有没有线程卡住。）

## 本章小结

* 钱包里没有钱，只有**私钥**（和一些为方便而缓存的交易记录）。币在区块链上。
* "是我的" = 锁是标准模板，且对应的私钥在我手里。
* **余额是现算的**：未花掉 + 已定稿 + （挖矿所得已满 120 个确认）的钱包交易的金额之和；零确认也算。
* v0.1.5 **整笔标记** `fSpent`，所以一花就得把那笔钱包交易里属于我的输出全花掉，多的找零。
* 找零付回**原币的同一个公钥**——和中本聪付给 Hal Finney 的那笔真实交易一样。
* 选币用原版的随机逼近算法；手续费靠"签名→算字节数→不够就加→重来"的循环凑出来。
* 善后：重启后重新入池、每 10 分钟重播、被重组掉的挖矿所得自动失效。

## 思考题

1. Alice 钱包里只有一枚 50 BTC 的成熟 coinbase。她付 10 BTC 给 Bob（手续费 0）之后，**立刻**再付 45 BTC 给 Carol，会成功吗？
2. 为什么私钥必须"立即写盘"，而不能像区块索引那样攒一批再写？
3. 有人说："我把钱包文件复制到两台电脑上，就有了两份钱。"错在哪里？如果两台电脑同时花同一笔钱会怎样？

<details><summary>参考答案</summary>

1. 失败（余额不足）。那枚 50 已经被整笔标记为已花；剩下的是 40 BTC 的找零（零确认，但可用）。40 < 45。
   如果第二笔是 35 BTC，则会成功——花的是那笔尚未确认的找零。
2. 假设矿工刚挖到一个区块，50 BTC 付给了一把新密钥，而这把密钥还在内存里没落盘，这时断电了——
   那 50 BTC 就永远没人能花了。区块索引丢了可以从区块文件重建，私钥丢了什么都救不回来。
3. 复制的是**钥匙**，不是钱。两台电脑看到的是区块链上同一批 UTXO。同时花同一笔钱就是一次双花：
   全网只会接受先被打包的那一笔，另一笔作废。（而且 v0.1.5 的钱包之间不会同步 `fSpent` 标志，
   另一台电脑的钱包会一直以为那笔钱还在——这是早期版本一个真实的坑。）
