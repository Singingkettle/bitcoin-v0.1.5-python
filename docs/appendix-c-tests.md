# 附录 C　测试地图

> 一份教材如果本身是错的，那比没有教材更糟。这份附录说明：本项目的 653 个自动化测试分别在验证什么，
> 你可以据此判断"这份代码到底靠不靠谱"。**测试本身也是很好的学习材料**——每个测试都是一个可运行的、
> 精确的小例子，回答"在某种情况下，系统应该怎样表现"。

## C.1　怎么运行

```powershell
pytest tests -q                         # 全部（约 3 分钟）
pytest tests\test_script.py -q          # 只跑某个文件
pytest tests -q -k "orphan"             # 只跑名字里带 orphan 的测试
pytest tests\test_wallet.py -v          # 显示每个测试的名字
```

最耗时的事情是挖矿。为了快，整个测试会话只挖**一次** 130 个区块的"种子链"（约 10 秒），
每个需要"有钱的链"的测试拿到的都是它的一份独立拷贝（见 `tests/conftest.py`）。

## C.2　四种验证手段

本项目的测试不只是"自己验证自己"。按可信度从高到低，用了四种手段：

| 手段 | 含义 | 例子 |
|---|---|---|
| **① 真实世界的数据** | 数据来自 2009 年中本聪的原版程序写进主网的内容 | 中本聪→Hal Finney 的交易；主网创世块；真实区块头 |
| **② 权威的外部向量** | 标准组织或算法作者公布的测试数据 | RIPEMD-160 官方向量；Bitcoin Core 的 Base58 向量；secp256k1 基点坐标；白皮书里的概率表 |
| **③ 独立实现交叉验证** | 两份互不相干的实现互相对答案 | 手写椭圆曲线 vs `ecdsa` 库；自带 RIPEMD-160 vs OpenSSL |
| **④ 行为规格** | 按原版源码的逻辑，断言"这种情况下应该发生什么" | 绝大多数测试 |

## C.4　怎样把测试当教材读

* **想知道某条规则的精确边界？** 找带 `boundary`、`limits`、参数化列表的测试。
  例如 coinbase 成熟度到底是"≥ 100"还是"> 100"？看 `test_chain.py::test_coinbase_maturity_boundary`。
* **想知道某种攻击会怎样？** 找名字里带 `exploit`、`double_spend`、`tamper`、`hostile` 的测试。
* **想知道原版有哪些怪癖？** 在测试的说明文字（docstring）里搜"原版"、"0.1.5"、"bug"。
* **想验证自己的理解？** 先猜一个测试会断言什么，再去看它；或者改动源码里的某一行，预测哪些测试会失败，然后运行验证。
  比如把 `blockchain.py` 里的 `if pindex.n_height <= self.best_height` 改成 `<`，会挂掉哪些测试？为什么？
