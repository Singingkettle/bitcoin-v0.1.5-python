# 第 8 章　区块与默克尔树

> **本章目标**：弄明白区块的结构、80 字节的区块头怎么"锁住"成百上千笔交易，
> 以及区块为什么能串成一条改不动的链。最后亲手重建比特币的创世块。
>
> **对应源码**：[bitcoin/block.py](../bitcoin/block.py)　　**实验**：[labs/lab07_block_merkle.py](../labs/lab07_block_merkle.py)

## 8.1　为什么要把交易打包成"区块"

第 1 章说过，双花问题的本质是"全网对交易的先后顺序达成一致"。
一笔一笔地排序太难了——交易每秒钟都在全球各处产生，在网络上以不同的速度传播。

中本聪的办法是**成批处理**：大约每 10 分钟，全网选出一个人，由他把这段时间里收到的交易打成一个包（**区块**），
并宣布"这一批交易排在之前所有区块之后"。区块内部交易的顺序、区块之间的顺序，合起来就是全网交易的总顺序。

白皮书里把这个机制叫做"时间戳服务器"：区块就像每 10 分钟盖一次的邮戳，
证明"这些交易在这个时刻之前已经存在了"。

## 8.2　区块的结构

```text
区块 CBlock
├── 区块头（固定 80 字节）
│   ├── nVersion          4 字节   版本号
│   ├── hashPrevBlock    32 字节   上一个区块的哈希          ← 把区块串成链
│   ├── hashMerkleRoot   32 字节   本区块全部交易的"指纹"    ← 锁住交易
│   ├── nTime             4 字节   时间戳（1970 年以来的秒数）
│   ├── nBits             4 字节   难度目标（压缩编码）       ┐
│   └── nNonce            4 字节   矿工不断尝试的那个数       ┘ 第 9 章
└── 区块体
    └── vtx[]             交易列表，第一笔必须是 coinbase
```

```python
class CBlock:
    def serialize_header(self, s: DataStream):
        s.write_int32(self.n_version)
        s.write_uint256(self.hash_prev_block)
        s.write_uint256(self.hash_merkle_root)
        s.write_uint32(self.n_time)
        s.write_uint32(self.n_bits)
        s.write_uint32(self.n_nonce)
```

4 + 32 + 32 + 4 + 4 + 4 = **80 字节**。

**区块的哈希（区块 ID）只对这 80 个字节计算**，和区块里有多少笔交易无关：

```python
    def get_hash(self) -> int:
        return int.from_bytes(hash256(self.header_bytes()), "little")
```

这是一个精心的设计：挖矿要对区块头做亿万次哈希（第 9 章），如果每次都要把几千笔交易重新哈希一遍，那就太慢了。
但只哈希区块头，怎么保证交易不被篡改呢？——靠区块头里的那个 `hashMerkleRoot`。

## 8.3　默克尔树

怎么用一个 32 字节的哈希代表一大堆交易？

最简单的想法：把所有交易的字节接在一起，算一个总哈希。这能防篡改，但有个缺点：
**要想证明"某一笔交易在这个区块里"，就得把整个区块的全部交易都拿出来**重新算一遍。

**默克尔树**（Merkle tree，1979 年由 Ralph Merkle 提出）是更聪明的办法：

```text
                        根  H(H12 + H34)                      ← 写进区块头
                       ╱               ╲
              H12 = H(H1 + H2)      H34 = H(H3 + H4)
               ╱        ╲            ╱        ╲
             H1         H2         H3         H4              ← 各笔交易的哈希
             │          │          │          │
            tx1        tx2        tx3        tx4
```

叶子是每笔交易的哈希；两两拼接再哈希，得到上一层；一层层往上，直到只剩一个——**默克尔根**。
这里的 H 就是第 3 章的 `hash256`。

某一层是奇数个怎么办？比特币的规则是：**最后一个和它自己配对**。

```python
    def build_merkle_tree(self) -> list[int]:
        tree: list[int] = [tx.get_hash() for tx in self.vtx]
        j = 0                       # 当前这一层在数组里的起始下标
        size = len(self.vtx)        # 当前这一层的节点数
        while size > 1:
            for i in range(0, size, 2):
                i2 = min(i + 1, size - 1)           # 没有右边的伙伴时，i2 == i：和自己配对
                combined = (tree[j + i].to_bytes(32, "little")
                            + tree[j + i2].to_bytes(32, "little"))
                tree.append(int.from_bytes(hash256(combined), "little"))
            j += size
            size = (size + 1) // 2
        return tree
```

返回的 `tree` 是把整棵树一层一层平铺成的一维数组，最后一个元素就是根。只有一笔交易时，根就是那笔交易的哈希。

### 性质一：牵一发而动全身

改动任何一笔交易的任何一个比特 → 它的哈希变了 → 它上面一层的哈希变了 → …… → 根变了
→ 区块头变了 → 区块哈希变了。

所以 **80 字节的区块头，通过默克尔根，锁死了区块里每一笔交易的每一个比特。**

### 性质二：高效的"存在性证明"

要证明 tx3 在区块里，不需要全部交易，只需要**从 tx3 到根的路径上的那几个"兄弟"哈希**：

```text
已知 tx3，别人给我 H4 和 H12：
    H3  = H(tx3)               我自己算
    H34 = H(H3 + H4)           用到别人给的 H4
    根  = H(H12 + H34)         用到别人给的 H12
然后和区块头里的默克尔根比较。
```

区块里有 N 笔交易，证明只需要 log₂N 个哈希：1000 笔交易只要 10 个，100 万笔也只要 20 个。

这是白皮书第 8 节"简化支付验证"（SPV）的基础：手机钱包不必下载几百 GB 的完整区块链，
只要保存所有的**区块头**（每个 80 字节，一年约 4 MB），再向全节点索要自己关心的那笔交易的默克尔证明即可。
实验 7 的第 3 步演示了这个过程。

> **一个后来才发现的小缺陷**："奇数时和自己配对"有个副作用——交易列表 `[1,2,3]` 和 `[1,2,3,3]`
> 会算出同一个默克尔根。2012 年有人发现这可以用来构造"哈希相同但内容无效"的区块来干扰节点（CVE-2012-2459）。
> 修复办法是拒绝含有重复交易的区块。`tests/test_tx_block.py` 里有一个测试演示了这个等式。

## 8.4　为什么叫"链"

每个区块头里都有上一个区块的哈希 `hashPrevBlock`。实验 9 里的真实输出：

```text
#101 哈希 00006400b63c9a3a…  它的"前一块"字段 = 0000d2dca220df16…
#100 哈希 0000d2dca220df16…  它的"前一块"字段 = 000096b7b0624231…
#99  哈希 000096b7b0624231…  它的"前一块"字段 = 00008118bedf4e40…
```

现在设想有人想篡改第 99 号区块里的一笔交易：

```text
改交易 → #99 的默克尔根变了 → #99 的区块头变了 → #99 的哈希变了
       → #100 里记的"前一块哈希"对不上了 → 必须改 #100 的区块头 → #100 的哈希也变了
       → #101 也对不上了 → ……
```

**改动历史上的任何一个区块，都必须连带重做它之后的所有区块。**
而"重做一个区块"意味着重新完成它的工作量证明（第 9 章）。区块埋得越深，要重做的工作就越多——
这就是"确认数越多越安全"的原因。

## 8.5　创世块

链总得有个开头。第一个区块（高度 0）叫**创世块**（genesis block），它没有"上一个区块"，`hashPrevBlock` 全是 0。
创世块是**写死在源码里**的：每个节点第一次启动时，不是从网络上下载它，而是用源码里的参数自己重建出来。
只有创世块相同的节点，才在同一条链上。

比特币的创世块由中本聪在 2009 年 1 月 3 日挖出。原版 `main.cpp` 里构造它的代码，翻译成本项目的 Python 是这样的
（[tests/test_genesis_vector.py](../tests/test_genesis_vector.py)）：

```python
    # 原版：txNew.vin[0].scriptSig = CScript() << 486604799 << CBigNum(4) << 时间戳文字
    script_sig = CScript().push_int(486604799).push_bignum(4).push_data(TIMESTAMP)
    script_pubkey = CScript().push_data(SATOSHI_PUBKEY).push_opcode(OP_CHECKSIG)
    txnew = CTransaction(vin=[CTxIn(COutPoint(), script_sig)],
                         vout=[CTxOut(50 * params.COIN, script_pubkey)])
    block = CBlock(n_version=1, hash_prev_block=0, n_time=1231006505,
                   n_bits=0x1D00FFFF, n_nonce=2083236893, vtx=[txnew])
    block.hash_merkle_root = block.get_merkle_root()
```

其中 `TIMESTAMP` 是一句话：

```text
The Times 03/Jan/2009 Chancellor on brink of second bailout for banks
```

这是英国《泰晤士报》2009 年 1 月 3 日的头版标题，说的是财政大臣即将对银行实施第二轮救助。
中本聪把它写进创世块的 coinbase 里，有两层用意：

* **技术上**，它证明这个区块**不可能早于**这一天被制造出来（没人能提前知道报纸的标题），
  也就是说中本聪没有在发布软件之前偷偷预先挖好一大堆区块；
* **思想上**，它是一句不动声色的注脚——这个系统为什么要存在。

用本项目的代码照上面的写法构造出来的区块：

```text
默克尔根 = 4a5e1e4baab89f3a32518a88c31bc87f618f76673e2cc77ab2127b7afdeda33b
区块哈希 = 000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f
整个区块序列化后 285 字节
```

和真实的比特币创世块**分毫不差**。这一个测试同时检验了：交易和区块的序列化、脚本的压栈编码、
默克尔树、双 SHA-256——任何一处和原版有出入，哈希就对不上。

> **一个细节**：`push_int(486604799)` 和 `push_bignum(4)` 为什么用了两个不同的方法？
> 因为原版 C++ 里 `<< 486604799`（一个普通整数）和 `<< CBigNum(4)`（一个大数对象）走的是两个不同的函数：
> 前者遇到 1~16 会编码成单字节的 `OP_1`~`OP_16`，后者**总是**编码成"压入数据"。
> 所以创世块的 scriptSig 以 `04 ffff001d  01 04` 开头（而不是 `04 ffff001d  54`）。
> 复刻这份代码时我们就在这里栽过跟头——哈希对不上，才发现这个区别。

### 本项目的私网创世块

本项目运行在自己的私有网络上，所以有自己的创世块，参数在 [params.py](../bitcoin/params.py) 里：

```python
GENESIS_TIMESTAMP_TEXT = b"D:/Projects/BTC 10/Jun/2026 Python re-creation of Bitcoin v0.1.5"
GENESIS_TIME = 1780272000     # 2026-06-01 00:00:00 UTC（必须是过去的时间）
GENESIS_BITS = 0x1F00FFFF     # 创世难度：大约每 65536 次哈希命中一次
GENESIS_NONCE = 7913
GENESIS_HASH = "00001fce11f81d65c4044b674cfdae590a2a07a84716c0f59fe39afaf1dd033f"
```

`GENESIS_NONCE` 和 `GENESIS_HASH` 是用 [tools/mine_genesis.py](../tools/mine_genesis.py) 挖出来之后回填的。
构造它的函数 `build_genesis_block()` 在 `blockchain.py` 开头，写法和主网的完全平行。

## 8.6　区块在磁盘上和内存里的样子

**磁盘上**：所有区块一个接一个追加写入 `blk0001.dat`，每条记录是"魔数(4) + 长度(4) + 序列化的区块"
（[db.py](../bitcoin/db.py) 的 `BlockFile`，格式与原版相同）。这个文件只追加、不修改。

**内存里**：不可能把所有区块都放在内存里。节点为每个已知的区块保留一条很小的"目录项"——`CBlockIndex`：

```python
class CBlockIndex:
    def __init__(self, block: CBlock, hash_: int, n_file_pos: int = 0):
        self.hash = hash_
        self.pprev: CBlockIndex | None = None       # 指向父块
        self.pnext: CBlockIndex | None = None       # 只沿着"最佳链"设置，指向下一个块
        self.n_height = 0                           # 高度（创世块是 0）
        self.n_file_pos = n_file_pos                # 区块在 blk0001.dat 里的偏移
        # 以及区块头各字段的副本……
```

`pprev` 把所有目录项连成一棵**树**（出现分叉时，一个父块会有多个子块）；
`pnext` 只在"当前认定的最长链"上设置。第 10 章会大量用到它们。

`block.py` 里还有一个类 `CBlockLocator`（区块定位器），是节点之间同步时用的，放到第 13 章再讲。

## 本章小结

* 区块 = 80 字节的区块头 + 交易列表；**区块哈希只对区块头计算**。
* 区块头里的**默克尔根**是全部交易的指纹，改任何一笔交易都会让它变化；
  证明"某交易在区块里"只需要 log₂N 个哈希。
* 每个区块头里有**上一个区块的哈希**，于是改动任何历史区块，其后所有区块都要重做。
* 创世块写死在源码里；里面那句报纸标题证明了它的制造时间。
* 本项目逐字段重建的主网创世块与真实的完全一致（285 字节，哈希 `000000000019d668…`）。

## 思考题

1. 一个区块有 9 笔交易，默克尔树一共有多少层？证明某一笔交易在区块里需要几个哈希？
2. 为什么区块哈希不把整个区块（包括所有交易）都算进去，而只算区块头？
3. 如果两个节点的创世块不同，它们连上之后会发生什么？

<details><summary>参考答案</summary>

1. 9 → 5 → 3 → 2 → 1，共 5 层（含叶子层）。证明需要 4 个哈希（每往上一层需要一个兄弟）。
2. 挖矿时要对区块头反复哈希上亿次，每次只哈希 80 字节极快；交易的完整性由默克尔根间接保证，一点不损失安全性。
   另外这也使得"只保存区块头"的轻量客户端成为可能。
3. 它们互相发来的每一个区块，追溯到最后都接不到自己的创世块上，全部会被当作无法连接的孤块。
   它们实际上处在两个互不相干的网络里——这正是本项目的私网不会和真正的比特币网络混淆的原因。
</details>
