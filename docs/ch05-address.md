# 第 5 章　地址

> **本章目标**：弄明白那串以 `1` 开头的比特币地址是怎么一步步从私钥变出来的，
> 以及这个设计里每一步的用意。
>
> **对应源码**：[bitcoin/base58.py](../bitcoin/base58.py)　　**实验**：[labs/lab04_address.py](../labs/lab04_address.py)

## 5.1　全景图

```text
   私钥（256 比特随机数）
     │   椭圆曲线乘法 ×G                          不可逆（第 4 章）
     ▼
   公钥（65 字节：04 + x + y）
     │   SHA-256，再 RIPEMD-160                  不可逆（第 3 章）
     ▼
   公钥哈希（20 字节）
     │   前面加版本字节 00，后面加 4 字节校验和，再做 Base58 编码      可逆
     ▼
   地址：1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa
```

**地址不是账户。** 它只是"公钥哈希"的一种便于人类抄写的写法。比特币的账本上没有"某个地址的余额"这种记录，
只有一笔一笔的交易输出，每个输出上挂着一把"锁"，锁里写着一个公钥哈希（第 6、7 章）。

## 5.2　为什么不直接用公钥当地址

把钱直接付给公钥也是可以的——v0.1.5 里挖矿所得就是直接付给公钥的（第 7 章的 P2PK）。
但普通转账用的是公钥的**哈希**，有两个好处：

**好处一：短。** 公钥 65 字节，哈希只有 20 字节。地址是要给人抄写、念给别人听的，越短越好。

**好处二：多一层保护。** 在你第一次花这个地址上的钱之前，你的**公钥从未在网络上出现过**，
全世界只见过它的哈希。万一将来有一天椭圆曲线被攻破了（比如足够强大的量子计算机问世），
攻击者面对一个只有哈希的地址仍然无从下手，因为他连公钥是什么都不知道。
只有在你花钱的那一刻才需要出示公钥（为了让别人验证签名）。

## 5.3　Base58

20 个字节如果用十六进制写是 40 个字符，如 `62e907b15cbf27d5425399ebf6f0fb50ebb88f18`。
能不能更短、更不容易抄错？

常见的做法是 Base64：用 64 个字符（大小写字母、数字、`+`、`/`）来表示，每个字符携带 6 比特。
中本聪在它的基础上做了修改，在 `base58.h` 的注释里解释了理由（大意）：

* 去掉 `0`（零）、`O`（大写 o）、`I`（大写 i）、`l`（小写 L）——这几个字符在很多字体里长得几乎一样；
* 去掉 `+` 和 `/`——只剩字母和数字后，双击鼠标就能选中整个地址，邮件软件也不会在符号处把它折成两行。

64 − 6 = 58，所以叫 **Base58**：

```python
ALPHABET = "123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz"
```

58 不是 2 的整数次方，所以不能像十六进制那样"几个比特对应一个字符"地切。
Base58 的做法是把整串字节当成**一个巨大的整数**，然后做"58 进制的短除法"——和小学里把十进制转二进制的方法一模一样：

```python
def encode(data: bytes) -> str:
    """EncodeBase58：把字节串当成一个大端的大整数，反复除以 58 取余数。"""
    n = int.from_bytes(data, "big")
    out = ""
    while n:
        n, rem = divmod(n, 58)
        out = ALPHABET[rem] + out
    # 大整数会"吃掉"开头的 0 字节，所以每个前导 0 字节要补一个 '1'
    pad = 0
    for byte in data:
        if byte == 0:
            pad += 1
        else:
            break
    return "1" * pad + out
```

最后那段"补 1"需要解释一下：字节串 `00 00 01` 当成整数就是 1，前面的两个 0 字节丢了。
为了能还原，规定每个前导的 0 字节写成一个 `'1'`（`'1'` 恰好是字母表里代表 0 的那个字符）。

**这就是为什么比特币地址都以 `1` 开头**：地址的第一个字节是版本号 `00`。

## 5.4　Base58Check：带校验和的 Base58

抄写地址最怕抄错。抄错一个字符，钱就打到了一个没有人拥有私钥的地址，**永远找不回来**，没有客服可以投诉。

所以地址里内置了一个**校验和**：

```python
def encode_check(data: bytes) -> str:
    """EncodeBase58Check：在末尾追加 4 字节校验和（对内容做两次 SHA-256 取前 4 字节）。"""
    return encode(data + hash256(data)[:4])
```

解码时重新算一遍校验和，对不上就拒绝：

```python
def decode_check(s: str) -> bytes:
    data = decode(s)
    if len(data) < 4:
        raise ValueError("Base58 字符串太短")
    payload, checksum = data[:-4], data[-4:]
    if hash256(payload)[:4] != checksum:
        raise ValueError("Base58 校验和错误")
    return payload
```

4 个字节的校验和有 2³² ≈ 43 亿种取值。地址抄错之后校验和**恰好**还能对上的概率是 43 亿分之一。
钱包软件在你点"发送"之前就会告诉你"地址无效"。

`tests/test_base58.py` 里有个测试把中本聪的创世地址的每一个字符轮流改掉，验证每一种改法都会被识别出来。

## 5.5　从公钥哈希到地址

把前面的零件装起来：

```python
ADDRESS_VERSION = 0     # 地址的版本字节。0 对应主网地址，所以地址都以字符 '1' 开头

def hash160_to_address(h160: bytes) -> str:
    """Hash160ToAddress：地址 = Base58Check(版本字节 0 + 20 字节的公钥哈希)。"""
    return encode_check(bytes([ADDRESS_VERSION]) + h160)

def pubkey_to_address(pubkey: bytes) -> str:
    """PubKeyToAddress：公钥 -> Hash160 -> 地址。"""
    return hash160_to_address(hash160(pubkey))
```

所以一个地址解码之后是 25 个字节：

```text
┌────────┬──────────────────────────────┬────────────┐
│ 版本 1 │      公钥哈希 20 字节        │ 校验和 4   │
└────────┴──────────────────────────────┴────────────┘
```

版本字节的作用是区分不同类型的地址（后来的比特币用 `05` 表示另一类以 `3` 开头的地址，测试网用 `6f`）。
v0.1.5 只认版本 `00`。

反方向——从地址还原出公钥哈希——是完全可逆的：

```python
def address_to_hash160(addr: str) -> bytes:
    payload = decode_check(addr)
    if len(payload) != 21 or payload[0] != ADDRESS_VERSION:
        raise ValueError("地址版本或长度错误")
    return payload[1:]
```

发送比特币时，钱包做的第一件事就是调用它：把你粘贴进去的地址变回 20 字节的公钥哈希，
然后写进新交易输出的"锁"里。

## 5.6　一个著名的例子

比特币创世块的那 50 BTC，付给了中本聪写死在源码里的一个公钥：

```text
公钥（65 字节）：
04678afdb0fe5548271967f1a67130b7105cd6a828e03909a67962e0ea1f61de
  b649f6bc3f4cef38c4f35504e51ec112de5c384df7ba0b8d578a4c702b6bf11d5f

SHA-256 -> RIPEMD-160（20 字节）：
62e907b15cbf27d5425399ebf6f0fb50ebb88f18

地址：
1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa
```

这大概是世界上最有名的比特币地址。十几年来不断有人往这个地址里打钱，以示致敬。
`tests/test_base58.py` 里的第一个测试就是验证本项目能从那个公钥算出这个地址。

顺带一提：本项目私网的创世块，收款公钥用的也是这一个（`params.py` 里的 `GENESIS_PUBKEY`）。
我们当然没有它的私钥，所以那 50 BTC 永远花不了——
不过即使有私钥也花不了，原因第 10 章会讲（创世块的交易根本不在"可花费"的索引里，真实的比特币也是如此）。

**改一改**：

## 本章小结

* 地址 = Base58Check( `00` + RIPEMD160(SHA256(公钥)) )。
* 私钥 → 公钥 → 公钥哈希，两步都**不可逆**；公钥哈希 ↔ 地址，**可逆**。
* 用哈希而不直接用公钥：更短；并且公钥在花钱之前不暴露。
* Base58 去掉了容易混淆的字符；4 字节校验和让抄错的地址几乎必然被发现。
* 地址只是"锁"上写的那个公钥哈希的人类可读形式；**账本上并没有"地址余额"这种东西**。

## 思考题

1. 一个地址解码后有 25 个字节。请说出这 25 个字节分别是什么。
2. 如果你把私钥弄丢了，但还记得地址，能找回钱吗？如果你把地址忘了，但还留着私钥呢？
3. 有 2¹⁶⁰ 种可能的地址，却有约 2²⁵⁶ 种可能的私钥。这意味着平均每个地址对应多少把私钥？这会带来安全问题吗？

<details><summary>参考答案</summary>

1. 第 1 字节版本号（`00`），第 2~21 字节公钥哈希，第 22~25 字节校验和。
2. 丢了私钥：找不回。地址到私钥要逆向走两个单向函数。留着私钥、忘了地址：没问题，
   从私钥可以重新算出公钥、再算出地址。**私钥就是一切。**
3. 平均每个地址对应 2⁹⁶ 把私钥。也就是说，理论上有很多把不同的私钥都能花你地址上的钱。
   但这不构成威胁：要"撞"到其中任何一把，仍然需要约 2¹⁶⁰ 次尝试（每试一把私钥，命中你这个地址的概率是 1/2¹⁶⁰）。
</details>
