# 第 2 章　数据的表示：字节与序列化

> **本章目标**：弄明白计算机里的数据长什么样——比特、字节、十六进制、大端小端；
> 以及比特币怎么把"一笔交易"这种结构化的东西变成一串字节（序列化）。
>
> **对应源码**：[bitcoin/serialize.py](../bitcoin/serialize.py)　　**实验**：[labs/lab01_bytes.py](../labs/lab01_bytes.py)

## 2.1　为什么要先学这个

比特币网络上传递的、硬盘上保存的、被哈希和签名的，全都是**一串字节**。
"一笔交易"在程序里是一个对象，有版本号、有输入、有输出；但要把它发给别人、或者算它的哈希，
就必须先把它按照一个**精确的、全世界统一的规则**变成字节。这个过程叫**序列化**（serialization）；
反过来从字节还原出对象，叫**反序列化**。

规则必须精确到每一个比特。原因在下一章你就会看到：哈希函数对输入极其敏感，
两个节点只要在序列化的规则上有一丁点分歧（比如一个把数字写成 4 字节、另一个写成 8 字节），
算出来的交易哈希就完全不同，它们就再也无法对"这是哪笔交易"达成一致了。

所以这一章虽然枯燥，却是地基。

## 2.2　比特、字节、十六进制

计算机里的一切都是 0 和 1。一个 0 或 1 叫一个**比特**（bit）；8 个比特叫一个**字节**（byte）。

一个字节有 2⁸ = 256 种可能的取值，也就是能表示 0 到 255。

直接写二进制太长了（`11111011001`），所以程序员习惯用**十六进制**：
用 `0 1 2 … 9 a b c d e f` 这 16 个符号，每个符号恰好对应 4 个比特。

| 十进制 | 二进制 | 十六进制 |
|---|---|---|
| 0 | 0000 | 0 |
| 9 | 1001 | 9 |
| 10 | 1010 | a |
| 15 | 1111 | f |
| 255 | 1111 1111 | ff |

**记住一条：两个十六进制字符 = 1 个字节。** 以后你看到一个 64 个字符的十六进制串（比如一个区块哈希），
马上要反应过来：这是 32 个字节，也就是 256 个比特。

Python 里：

```python
>>> 255 == 0xff == 0b11111111
True
>>> bytes.fromhex("f9beb4d9")          # 十六进制字符串 -> 字节
b'\xf9\xbe\xb4\xd9'
>>> b'\xf9\xbe\xb4\xd9'.hex()          # 字节 -> 十六进制字符串
'f9beb4d9'
```

## 2.3　一个数占几个字节：定长整数

数字 1 在数学上就是 1，但在计算机里你得说清楚"用几个字节装它"。比特币的协议里用到的有：

| 名字 | 字节数 | 能表示的范围 | 在比特币里用来装什么 |
|---|---|---|---|
| `uint8` | 1 | 0 ~ 255 | 单个 opcode |
| `uint16` | 2 | 0 ~ 65535 | 网络端口 |
| `int32` / `uint32` | 4 | 约 ±21 亿 / 0 ~ 42 亿 | 版本号、时间戳、难度、nonce |
| `int64` | 8 | 约 ±9.2×10¹⁸ | **金额** |
| `uint256` | 32 | 0 ~ 2²⁵⁶ | 哈希值 |

`int` 是有符号的（能装负数），`uint` 是无符号的（u = unsigned）。

**关于金额**：比特币里的金额永远是整数，单位是"聪"（satoshi），1 BTC = 100,000,000 聪。
`params.py` 里：

```python
COIN = 100_000_000            # 1 BTC = 1 亿聪（satoshi）。全项目金额一律用"聪"的整数
CENT = 1_000_000              # 0.01 BTC，手续费体系的基本单位
```

为什么不用小数？因为计算机里的小数（浮点数）有舍入误差，`0.1 + 0.2` 在 Python 里等于 `0.30000000000000004`。
记账是不允许有这种误差的——尤其是当全世界成千上万台电脑必须算出**完全相同**的结果时。

2100 万 BTC = 2.1×10¹⁵ 聪，远小于 `int64` 的上限 9.2×10¹⁸，装得下。

## 2.4　大端与小端

一个 4 字节的整数 `0x12345678`，它的 4 个字节是 `12`、`34`、`56`、`78`。
把它写到内存或者网线上的时候，先写哪个字节？有两种流派：

```text
大端（big-endian）   ：12 34 56 78     高位在前，和人类写数字的习惯一样
小端（little-endian）：78 56 34 12     低位在前，Intel/AMD 的 CPU 在内存里就是这么放的
```

名字来自《格列佛游记》里为"鸡蛋该从大头敲还是小头敲"而打仗的两个国家——意思是这纯粹是个约定问题，没有对错。

**比特币几乎所有的整数都用小端。** 原因很朴素：中本聪是在 Windows + Intel CPU 上写的程序，
他直接把内存里的字节原样写了出去。

```python
>>> (1).to_bytes(4, "little").hex()
'01000000'                              # 版本号 1 在每笔交易的开头就是这 4 个字节
>>> (50 * 100_000_000).to_bytes(8, "little").hex()
'00f2052a01000000'                      # 50 BTC。以后你会在很多 coinbase 交易里认出它
```

### ⚠️ 全教程最大的一个坑：哈希的显示顺序

256 位的哈希值在比特币程序里被当作一个巨大的整数，它**也是按小端存储和传输的**。
但是人们在网页上、在日志里显示它的时候，习惯按大端写（高位在前，这样开头的一串 0 才显眼）。

于是同一个哈希有两副面孔，恰好是**字节顺序完全颠倒**的关系：

```text
区块浏览器上显示的创世块哈希：000000000019d6689c085ae165831e934ff763ae46a2a6c172b3f1b60a8ce26f
它在字节流里实际的样子：      6fe28c0ab6f1b372c1a6a246ae63f74f931e8365e15a089c68d6190000000000
```

在本项目里，哈希值在程序内部用 Python 的 `int` 表示（不存在顺序问题），只在两个地方转换：

```python
def uint256_to_bytes(n: int) -> bytes:        # 写进字节流：小端
    return n.to_bytes(32, "little")

def uint256_to_hex(n: int) -> str:            # 显示给人看：大端
    return n.to_bytes(32, "little")[::-1].hex()
```

`[::-1]` 是 Python 里"把序列倒过来"的写法。以后每当你发现自己算出的哈希和别处查到的"对不上"，
先检查是不是忘了颠倒字节序——十有八九是。

## 2.5　变长整数（CompactSize）

一笔交易有几个输入？一段脚本有多长？这些"个数"和"长度"绝大多数时候是很小的数（1、2、25、107），
偶尔会很大。如果一律用 4 个字节装，太浪费；一律用 1 个字节装，又装不下大的。

比特币的办法是**变长整数**：小数字用 1 个字节，大数字先写一个"标记字节"说明后面跟几个字节。

| 数值范围 | 编码 | 总字节数 |
|---|---|---|
| 0 ~ 252 | 直接写这个数 | 1 |
| 253 ~ 65535 | `fd` + 2 字节小端 | 3 |
| 65536 ~ 2³²−1 | `fe` + 4 字节小端 | 5 |
| 更大 | `ff` + 8 字节小端 | 9 |

对应的源码（[serialize.py](../bitcoin/serialize.py)）：

```python
def ser_compact_size(n: int) -> bytes:
    if n < 253:
        return struct.pack("<B", n)
    if n <= 0xFFFF:
        return b"\xfd" + struct.pack("<H", n)
    if n <= 0xFFFFFFFF:
        return b"\xfe" + struct.pack("<I", n)
    return b"\xff" + struct.pack("<Q", n)
```

`struct.pack` 是 Python 标准库里"把数字打包成字节"的函数。格式串里 `<` 表示小端，
`B`/`H`/`I`/`Q` 分别是 1/2/4/8 字节的无符号整数。你会在 `serialize.py` 里看到每个格式串都以 `<` 开头——
这就是"比特币全用小端"在代码里的样子。

读的时候有一道安全检查：

```python
        if n > MAX_SIZE:
            raise SerializationError("ReadCompactSize() : 长度超过上限")
```

`MAX_SIZE` 是 32 MiB。没有这一行的话，坏人发来一条消息声称"后面有 40 亿个元素"，
你的程序就会老老实实去申请 40 亿个元素的内存，然后崩溃。**永远不要相信网络上发来的长度字段**——
这是写网络程序的第一条纪律。

## 2.6　变长的数据：字节串与数组

有了变长整数，变长的数据就好办了：**先写长度，再写内容。**

```python
    def write_string(self, s: bytes):
        """字节串 / vector<unsigned char>：先写变长长度，再写内容。"""
        self.write_compact_size(len(s))
        return self.write(s)

    def write_vector(self, v, write_elem):
        """数组：先写元素个数（变长整数），再逐个写元素。"""
        self.write_compact_size(len(v))
        for elem in v:
            write_elem(elem)
        return self
```

交易里的脚本是字节串；交易的输入列表、输出列表，区块里的交易列表，都是数组。

## 2.7　DataStream：带游标的字节缓冲区

原版 C++ 里有个类叫 `CDataStream`，本项目对应的是 `DataStream`。它就是一段字节 + 一个"读到哪儿了"的游标：

```python
class DataStream:
    def __init__(self, data: bytes = b"", n_type: int = 0, n_version: int = 0):
        self.buf = bytearray(data)
        self.cursor = 0
```

* **写**：永远追加到末尾。`write_int32`、`write_int64`、`write_uint256`、`write_string`……
* **读**：从游标处读出若干字节，游标向后移。`read_int32`、`read_int64`……每个 `write_xxx` 都有对应的 `read_xxx`。

读的时候如果字节不够，抛 `SerializationError`——同样是为了防范网络上发来的残缺或恶意数据。

序列化一个对象，就是**按固定的顺序**把它的每个字段写进去；反序列化就是按**同样的顺序**读出来。
没有字段名，没有分隔符，全靠双方对顺序的约定。比如第 6 章会讲的交易：

```python
    def serialize(self, s: DataStream):
        s.write_int32(self.n_version)                           # 1. 版本号，4 字节
        s.write_vector(self.vin, lambda i: i.serialize(s))      # 2. 输入列表
        s.write_vector(self.vout, lambda o: o.serialize(s))     # 3. 输出列表
        s.write_uint32(self.n_lock_time)                        # 4. 锁定时间，4 字节
```

这种格式极其紧凑（没有一个多余的字节），代价是人眼完全没法直接读。不过别担心，
第 6 章我们会拿着"手术刀"把一笔真实的交易一个字节一个字节地切开。

## 本章小结

* 两个十六进制字符 = 1 字节；64 个十六进制字符 = 32 字节 = 256 比特。
* 比特币的整数全是**小端**；金额是 8 字节整数，单位是聪，**绝不用小数**。
* 哈希值在字节流里是小端，显示给人看时是大端——**字节顺序相反**，这是最常见的坑。
* 变长整数让小数字只占 1 字节；变长数据的格式是"长度 + 内容"。
* 序列化 = 按固定顺序写字段；全网必须使用逐比特相同的规则。
* 读取网络数据时，**任何长度字段都要先检查上限**。
